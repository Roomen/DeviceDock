# 插件契约 v1

客户端插件包、GitHub Release 资产、沙箱隔离与宿主 RPC 的实际做法；只写现状、禁止项和坑。

## 包格式与清单

- 插件只在桌面客户端（`html[data-runtime='tauri']`，功能 id `plugins`）实现，网页版与移动端门控关闭，不显示任何插件入口也不加载插件执行路径。
- 每个插件独立 GitHub 仓库、各自 CI 构建发布；包根必须放 `manifest.json`，所有要由 `ddplugin://` 提供的文件（含 `entry`、脚本、样式、图标、SDK）都必须列在 `integrity` 里。
- `manifest.json` 字段（严格校验、`deny_unknown_fields`）：`schemaVersion:1`、`id`（`^[a-z0-9][a-z0-9.-]{0,62}[a-z0-9]$` 或单字符）、`name`（1–48 字符）、`version`（完整 SemVer 式 `主.次.修订`，可带 `-预发布` / `+构建`，整串只认 `[0-9A-Za-z.+-]`，预发布 / 构建标识符非空且点分隔）、`apiVersion:1`、`kind:"web"|"native"`、`entry`（包内相对路径，`web` 插件必须是 `.html`/`.htm`）、`icon?`（lucide 图标名或包内相对 `.svg` 路径，后者必须在 `integrity` 中声明）、`capabilities:[...]`（无重复）、`platforms?:["macos","windows","linux"]`（省略表示全桌面平台）、`native?`（仅 `kind:"native"` 允许）、`integrity:{ "<包内相对路径>": "sha256-<64 位十六进制>" }`、`homepage?`、`license?`。
- 版本号会拼进 `plugins/<id>/<version>/`：`valid_version` 禁止 `/`、`\`、`..` 与控制字符，`store::checked_version_dir` 落盘前再独立确认目标是插件目录下的单层子目录；`version_dir` 对非法版本退到不存在的 `.invalid-version`，`ddplugin://` 路径解析也用同一判据，后缀里塞 `../../` 越不出目录。
- 解压拒绝重复文件条目、大小写碰撞（`index.html` 与 `INDEX.html` 在大小写不敏感文件系统上指向同一文件）、**Unicode NFC 归一化碰撞**（`café` 的组合/预组合写法）、文件与目录同名、把文件当目录用；路径表键按 NFC + 小写比较，写入用 `create_new` 独占创建，不能靠解压顺序覆盖已校验内容。
- 包内路径只允许以 `/` 分隔的普通相对路径段：禁止空段、`\`、以 `/` 开头、`.` / `..`、控制字符、`:`、结尾空格或点、以及 Windows 保留设备名（`con`/`prn`/`aux`/`nul`/`com1..9`/`lpt1..9`）；校验见 `desktop/src-tauri/src/plugins/manifest.rs` 的 `safe_rel_path`。
- 单包硬上限：最多 4000 个文件、单文件不超过 8 MiB、整包解压不超过 64 MiB、`manifest.json` 不超过 256 KiB；解压时禁止符号链接、硬链接、设备节点与 FIFO。

## 资产命名与下载校验

- 用户填写仓库根地址 `https://github.com/<owner>/<repo>`（可带 `@<tag>` 指定版本，不带子路径）安装；宿主请求 GitHub Release API（最新 release 或指定 tag）。
- 资产下载**不信任** release 元数据里的 `browser_download_url`：用资产 `id` 自己拼 `https://api.github.com/repos/<owner>/<repo>/releases/assets/<id>`（`Accept: application/octet-stream`），初始 URL 再校验一次域名；重定向逐跳限制为 GitHub / `*.githubusercontent.com` 等白名单 HTTPS 域名、最多 5 跳，`bearer_auth` 标记的敏感头由 reqwest 在跨 host 时剥离，令牌不会跟到第三方地址。`id` 为 0 的资产直接拒绝。每个请求只设**一个** `Accept`（release API 是 `application/vnd.github+json`，资产下载是 `application/octet-stream`）：reqwest 的 `.header()` 是追加语义，两个 Accept 会让 GitHub 可能返回资产元数据而不是文件内容。
- 资产选择规则：优先名为 `devicedock-plugin.zip` 或 `devicedock-plugin.tar.gz` 的资产，其次匹配 `*.devicedock-plugin.zip` 或 `*.devicedock-plugin.tar.gz`；同一 release **必须**存在同名的 `<资产名>.sha256` 校验文件（支持 `sha256sum` 的 `<64hex>  <文件名>` 格式），缺失或校验不符直接拒绝，不做无校验降级。
- 下载与解压全部在 Rust 侧（`desktop/src-tauri/src/plugins/`）完成：先校验整包 `.sha256` → 解压到 `app_data_dir/plugins/.staging-<随机>/` → 解析 `manifest.json` → 按 `integrity` 对磁盘文件逐个复核 SHA-256 → 原子重命名切换到 `app_data_dir/plugins/<id>/<version>/` 并清理旧版本目录（保留同级 `storage.json`）；任何一步失败立即删除临时目录回滚。
- 安装与更新分两步：`plugin_inspect` / `plugin_check_update` 先下载校验并读出清单、版本差异与能力变化，界面展示确认卡（名称、来源仓库、版本、包 SHA-256 前 12 位、申请能力的人话说明与新增能力标记），用户点击授权后 `plugin_install` 核对 `expectedSha256` 一致才落盘；包摘要在确认后发生变化的会拒绝安装。
- 安装恢复**只看实际文件系统状态**（target / backup / staging 三个路径 + 两份完整包身份 oldId/newId + 新旧 state 条目），阶段字段只用于诊断；完整决策表与逐行单测见 `desktop/src-tauri/src/plugins/store.rs` 顶部注释与 `p4-report.md`「回修 4」。身份摘要对目录**全部文件**（含 manifest.json 与 integrity 未列出的文件）按相对路径排序后算「路径 + 长度 + sha256」。能确定旧版完整 → 还原旧目录与旧 state；能确定新版完整且 state 已是新 → 补完清理；新版完整但 state 仍旧 → 回滚到旧版（不让旧授权配新 manifest）；其它任何组合（目标缺失、身份对不上、备份缺失、state 未知）→ **不删任何副本**，隔离为待修复。
- `plugin_install` 的 `expectedSha256` **必填且必须是 64 位十六进制**，与本次下载包摘要比对；`expectedCurrentVersion` / `expectedCurrentSha256` 把 `inspect`/`checkUpdate` 时的已安装状态带回，提交前在锁内用 `baseline_matches` 重新核对，并发变更（版本或摘要变了）一律要求重新确认，避免能力差异展示过期。

## 隔离模型与安全边界

- `web` 插件 UI 在主视图区（`#views > .plugin-view`）用 `<iframe sandbox="allow-scripts" referrerpolicy="no-referrer">` 加载，**绝不授予 `allow-same-origin`**：插件文档处于 opaque origin，拿不到宿主 DOM、`localStorage`、`sessionStorage`、`indexedDB` 或 `__TAURI__` 全局量。
- `iframe.src` 走 Tauri 自定义协议 `ddplugin://`（macOS/Linux 为 `ddplugin://localhost/<id>/<version>/<path>`，Windows WebView2 为 `http://ddplugin.localhost/<id>/<version>/<path>`，由 `convertFileSrc` 统一生成）；协议处理器只返回「当前已安装 + 已启用 + 版本匹配 + 列在 `manifest.integrity` 中 + 实时读取复核 SHA-256 通过」的普通文件，停用或卸载后立即返回 404。
- `ddplugin://` 响应头固定带严格 CSP：`default-src 'none'; script-src <scheme> 'unsafe-inline'; style-src <scheme> 'unsafe-inline'; img-src <scheme> data:; font-src <scheme> data:; media-src <scheme>; connect-src 'none'; form-action 'none'; base-uri 'none'`，插件不能直接发外部网络请求，所有外部交互必须经宿主 RPC。
- **能力白名单是 Web 插件的真实权限边界**：插件通过 `window.parent.postMessage({ __devicedock: 1, id, method, params }, '*')` 发请求，宿主 `js/plugin-host.js` 先按 `event.source === view.iframe.contentWindow` 识别来源插件实例，再由 `js/plugin-rpc.js` 的 `authorize(capabilities, method)` 逐次核对该插件已授权的能力，未声明对应能力的调用一律返回 `capability_denied`。先做 O(1) 准入（在飞 ≤ 8、每秒 ≤ 60 次，无效 / 超大 / 高频消息都先计数），再做**有界**遍历：消息 256 KiB、参数 128 KiB，`estimateSize` 的节点数与字符数都受预算限制，大数组不整体压栈（超预算立即返回 `Infinity`）；超限回 `too_large` / `rate_limited`。`app.saveFile` 另有 8 MiB 导出上限，`app.storageSet` 单值 64 KiB。
- 宿主 → 插件事件分**两类**，分类表见 `js/plugin-rpc.js` 的 `STATE_EVENTS` / `DATA_EVENTS`：**状态事件**（`ready`、`theme`、`theme-change`、`device.ports`、`device.lane`、`device.ble-error`、`claim.state`、`app.busy`、`app.locale`——连接 / 断开 / 占用变化 / 主题 / 界面语言 / 设备信息变更）走独立合并窗口，按事件类型只保留最新态并**保证送达**（限流期间合并，窗口切换或定时器到点后整批补发，不占数据流配额、不算丢弃）；**数据流事件**（`serial.rx`/`tx`、`protocol.frame`、`device.ble`）按插件限流（每秒 ≤ 120），超额丢弃；**`claim.rx` / `claim.gap` 是直发事件**（`DIRECT_EVENTS`），不经过任何配额：`claim.rx` 由宿主按 claim 合批（≤ ~60 条/秒、4 批在途背压、单条上限 8 MiB），`claim.gap` 是丢弃报告必须送达；本窗口第一次丢弃立刻发 `events.dropped` 计数事件，窗口切换时补报剩余计数，插件据此知道数据有缺口。`events.dropped` 自身是优先级提示，直接发送、不受限流。`claim.state` 在 `claim.acquire/open/close/release` 时推送，让占用变化不会因为串口高频数据而丢。
- 逐版本信任也覆盖**同版本重装**：已加载 iframe 的版本、入口、包 SHA-256 或授权集合任一变化（`DeviceDockPluginRpc.pluginChanged`）就销毁旧 iframe、等资源收尾完成后再加载新确认的包；不能让旧代码继续拿新能力表授权。
- `protocol.read` 的 `protocol.info` / `protocol.call` 经 `serialLanes.callInIsolatedLane`（内部 `inLane`）换入该路协议与该路实时 `skSession` 的**快照拷贝**（用完即丢，不回写）/ 隔离 ansi 状态：解析能读到这一路已有的基准水量，但插件传入的字节改动不了实时会话，双路 A/B 不串；**协议函数按同步契约注册**：`js/protocol-contract.js` 的 `normalizeProtocolDef` 用 `AsyncFunction` 构造器 / `Object.prototype.toString` 在注册层拒绝 async 实现（`tx` 测试执行器不受此限制，见 `docs/protocol-contract.md`），`plugin-api.js` 调用前再挡一次，`inLane` 里的 thenable 检查只作兜底——异步实现根本不会被调用，也就不会在隔离上下文退出后继续访问已恢复的全局状态。
- `native` 插件是预留给需要本地可执行文件场景的扩展类型（`manifest.json` 保留 `kind:"native"` 与 `native` 字段校验，当前安装阶段拒绝落地并提示尚未开放）：**一旦启用本地子进程，它就是操作系统级本地进程，`capabilities` 声明对它只是宿主桥层的权限列表，不是操作系统沙箱**，不要把 `capabilities` 当成对本地二进制的沙箱承诺。

## 宿主 API 与能力表

- `device.read`：`device.listPorts`（在位/已授权串口的文档内 `key`、口名、产品名、别名、VID/PID、序列号、当前归属与占用者）、`device.listBle`、`device.listClassic`、`device.bleScan`（启停 BLE 扫描，插件关闭时自动停止）、`device.lanes`（当前可见的 `S` 或 `A`/`B` 路连接态、协议、参数、端口信息）；宿主向拥有该能力的插件推送 `device.ports`（热插拔/列表变化）与 `device.lane`（通道连接态变化）事件。
- 字节参数（`serial.write` / `claim.write` 的 `bytes`）接受四种形状：0..255 整数数组、十六进制串、ArrayBuffer 视图（`Uint8Array` 等，按视图覆盖的 `byteOffset` / `byteLength` 取，不读整块底层缓冲）、`ArrayBuffer`；单次上限 64 KiB，超过报 `too_large`，其它形状（含类数组对象）报 `bad_request`。所以插件可以把收到的 `claim.rx`（`Uint8Array`）切片后原样写回。请求大小估算对字节缓冲按 `byteLength` 计，不逐下标遍历。
- `serial.io`：`serial.write({ lane, bytes })`（向当前可见且已打开的 `S`/`A`/`B` 路写入，单次上限 64 KiB；固件页自己的连接不是 lane，插件看不到也写不了）；宿主经 `window.serialByteTap` 向拥有该能力的插件实时推送 `serial.rx` 与 `serial.tx`（`{ lane, at, bytes }`）。
- `serial.claim`：`claim.acquire({ portKey, mode })`（声明 `exclusive` 或 `shared` 占用某个串口，登记到 `window.serialPortClaims`，宿主的 `SerialHub.busyOwnerOfPort`、选口冲突提示「该口已被插件『…』占用」与热插拔 `findRebindSession` 都认这个声明，通信页各路与固件页的连接选口时同样认）、`claim.release`、`claim.list`、`claim.open` / `claim.close` / `claim.write` / `claim.ack`（直接读写被插件占用的端口）。插件的串口连接**只受物理口独占约束**：`claim.acquire` 经 `SerialHub.sessionOwnerOfPort` 拒绝正被任何会话占着的口（通信页 S/A/B 或固件页的连接 F：打开、打开中、尚未确认释放、正在换上），与通信页哪一路可见、是否打开、主发路是否被事务钉扎都无关；关着但仍记着该口的会话不算占用。`claim.open({ claimId, baudRate?, signals? })` 的可选 `signals` 是 `{ dataTerminalReady?: boolean, requestToSend?: boolean }`：打开成功后调端口的 `setSignals` 设置这两条控制线（不给或空对象就不调）；只收这两个键且值必须是布尔，否则 `bad_request` 且不打开；端口没有 `setSignals` 时报 `unsupported`、不打开，不静默忽略；设置失败时宿主关掉刚打开的口并报错，不算打开。收到的数据以 **`claim.rx` 合批事件**推给该插件：读循环把块攒进每个 claim 自己的缓冲，按 16 ms 时间窗或 256 KiB 字节阈值刷一条，载荷 `{ claimId, gen, seq, offset, at, bytes }`——`bytes` 是 **`Uint8Array`**、`gen` 是该 claim 第几次 `claim.open`（从 1 起，每次 open +1）、`seq` 在同一 gen 内从 1 单调递增、`offset` 是本批首字节在该 gen 字节流里的绝对偏移（含已丢弃的字节）、`at` 是本批第一块的到达时间。**插件必须按字节流解析，不得假设「一个事件一帧」**；判断缺口用 `offset !== 上一批 offset + 上一批 bytes.length`。
- **背压（ACK 只前进、跨 gen 累计）**：每个 claim 允许 4 批「已发未确认」在途，额度**跨 `gen` 累计**：记账按 `{ gen: { rxSeq, ackedSeq } }` 分开存在 claim 上，在途总数 = 各 gen `rxSeq - ackedSeq` 之和；所以反复 `claim.close` / `claim.open` **不会重置额度**，旧 gen 没被确认的批次继续占配额，直到插件 ack 它们（旧 gen 的 ack 照样生效，该 gen 全部确认后条目自动删除）。到上限就停发、数据继续留在 8 MiB 缓冲里。 当前 gen 的记账**永不删除**（同一 gen 内 `seq` / `ackedSeq` 单调，删掉重建会让迟到的旧 ACK 确认新批次）；只有「非当前 gen 且在途 0」的条目才回收，关闭 / 释放时连当前 gen 也在在途 0 时一起回收（下次 open 开新 gen），所以 `rec.gens` 条目数 ≤ 有在途批次的 gen 数 + 1。
- `claim.ack({ claimId, gen, seq })` 累积确认：宿主只记该 gen 已确认的最高 `seq`，**不前进的（重复 / 更小的）ACK 一律忽略**，未知 gen / 超前 `seq` 同样忽略且不报错；只能确认本插件自己的 claim。SDK 的 `claim.onRx` 对同一 claim **串行**调用回调（上一批含 Promise 结束才轮到下一批，跨 gen 也按到达顺序），每批结束后按序 ack；回调抛错或 Promise 拒绝时**仍 ack**（视为已消费，避免把宿主卡死在背压里），同时调用 `setClaimErrorHandler` 注册的处理器（没有就 `console.error`）。
- `claim.ack` 归 `serial.claim` 能力，**不计入每秒 60 次 RPC 配额、也不单独限流**（它是累积确认，丢掉一条会让收发停住；重复的 ACK 天然幂等）；它走单独的轻量校验：直接读固定字段（不枚举对象）、`claimId` 为 1–64 字符字符串、`gen`/`seq` 为安全正整数，多余键忽略；畸形直接丢弃不回包，通过后仍要过 `serial.claim` 能力校验。SDK 用**即发即忘**的方式发 ACK（`claim.ack()` 返回 `undefined`，宿主快速路径本就不回包）。
- **丢弃报告（合并、有界）**：缓冲超过 8 MiB 时丢最早的字节（单个超过 8 MiB 的块截掉其前缀、**复制**保留尾部，不持有原底层缓冲），丢弃字节并进**每个 claim 至多一条**待发记录 `{ offset, bytes, reason }`（`offset` 保留首次丢弃起点、连续丢弃累加 `bytes`、`reason` 取最先记录的那条）。缺口**只在两处发出**：① 即将真正发送一批 `claim.rx` 之前（随这批一起受在途 ≤ 4 约束，因此缺口事件也随之有界）；② 关闭 / 释放收尾时若有待发缺口（含 `closing`）发出**一条**合并缺口。**缺口在插件恢复确认后随下一批数据先送达**；插件始终不确认时（其消息循环已经停下）宿主**不另发缺口**，这是有意为之——没有可接收方。**关闭收尾的合并缺口每次关闭至多一条**：`claim.open` / `claim.close` 本身是计配额、需要等回包的 RPC，因此这种缺口的数量受 RPC 在途上限约束。数据合批的 16 ms 定时器只负责把缓冲数据成批发出去，不承担缺口发送，且在途已满时既不清除也不重设它的截止时间。发出去的 `claim.gap` 为 `{ claimId, gen, offset, bytes, reason }`（`reason`: `overflow` | `closing`），走直发路径、不受任何配额；**不再用 `events.dropped` 表达 claim 丢弃**。
- 收尾：`claim.close` / `claim.release` 与停用 / 更新准备**不越过在途上限**——能发多少发多少（含关闭途中刚兑现的读块），发不下的残余并入 `reason: "closing"` 的缺口而不是强发；iframe 已销毁则直接丢弃且不再报告；重新 `open` 开新 `gen` 时 `ackedSeq` / 在途计数一并归零（旧 gen 的 ACK 被忽略）。定时器随 claim 释放。
- `protocol.read`：`protocol.info({ lane })`（读取该路当前协议 id、名称、`fields` 与 `queries`）、`protocol.call({ lane, fn, args })`（调用协议的 `parseFrame` / `formatFrame` / `findFrame` / `metrics` / `buildRead` / `buildWrite` / `matchResponse` / `logView` / `byteMap` / `buildDownFrame`，返回值经 JSON 克隆剔除函数与 DOM 引用）；宿主推送 `protocol.frame` 事件。
- `log`：`log.write({ text })`（向宿主当前日志区写入带 `[插件名]` 前缀的系统行）、`log.recent({ count })`（读最近最多 500 行日志摘要）、`log.export`（导出当前日志纯文本）。
- `app`：`app.theme`（当前 `{ theme, tokens }`）、`app.platform`（系统、运行时、画像、通道数、应用版本与插件自身身份）、`app.busyAcquire({ label })` / `app.busyRelease({ busyId })`（注册/注销应用更新阻断源，`js/app-update.js` 的 `blockers` 会把插件持有的 busy 标签并入阻断原因，阻止更新下载与安装）、`app.storageGet` / `app.storageSet` / `app.storageRemove`（按插件 id 隔离在 `app_data_dir/plugins/<id>/storage.json`，最多 256 个键、单值 64 KiB，卸载插件时随目录一并删除）、`app.saveFile`、`app.dialog`（转调 `AppDialog.alert/confirm/prompt`）、`app.notify`。

## 主题、生命周期与令牌存储

- **待修复是硬门槛**：恢复失败时 `.repair.json` 与 state 条目里的 `repair` 字段两处至少一处必须写入成功（分别对应 `scheme.rs` 的 404 与 `plugin_set_enabled` 的拒绝启用）；两处都失败时在本次进程内存里记住并让该插件不可用。左栏 `visible()` / `openPlugin` 都排除 `repair` 插件，管理面板顶部常显「重试恢复 / 移除」。插件根目录 / 跨进程锁获取失败时 `PluginsState::init` 不失败，整个子系统标记不可用（`plugin_status`），管理面板说明原因，客户端照常启动。
- 状态事件**按键合并**：`device.lane` 按 lane 分键（A/B 各自最新），`device.ports` 是「列表已变化，请重新查询」的单一通知（不带增量），其它状态事件按事件名 + 主体 id 分键；数据流事件仍限流丢弃并报 `events.dropped`。分类与键函数见 `js/plugin-rpc.js` 的 `STATE_EVENTS` / `stateEventKey`。
- **明令禁止协议用普通函数返回 Promise / thenable**：注册层拒绝 `async` 声明、调用前再挡一次、调用后的 thenable 检查只作兜底，**无法取消已经安排的回调**；异步实现会在 `inLane` 恢复全局状态后继续跑，必然串路。宿主不再追加机制，详见 `docs/protocol-contract.md`。
- **读路径用跨进程共享锁**：`plugins/.lock` 同一把 fs2 文件锁——`plugin_list` 与 `ddplugin://` 每次请求在**整个读取过程**（读 state、manifest、文件内容）持共享锁（`store::read_lock`，约 120 ms 短等待），安装 / 卸载 / 启用切换持排他锁。拿不到共享锁时 `plugin_list` 把全部插件标 `installing`（`enabled=false`）、`ddplugin://` 统一 503（`ServeGates.all_busy`）；左栏 / `openPlugin` 也排除 `installing`。进程内 `PluginsState.active` 只作快速路径，正确性由跨进程锁保证。**取锁与取门禁的先后是硬约束**：`serve` 先 `store::read_lock`、再在锁内 `state.serve_gates()` 与 `load_state`；`plugin_list`（`list_all_state`）同样先取共享锁、再在锁内读 `blocked` / `active`；安装返回值也经 `read_info_locked` 在共享锁下重新读 state + manifest 再组装，避免把上一次的 state 与这一次的 manifest 混在一起。内存禁用集合命中时列表直接 `enabled=false`（不是只写一句原因），不会把插件报成可用。安装任何失败都在**释放锁前**用 `finalize_failed_install` 复用决策表恢复或隔离，是否删 staging 由决策结果决定。
- **staging 可清理判据按平台分流**：`reclaimable(age, policy, pid_gone, lock_held)` 是纯函数——先要求「超过 15 分钟」且「同级 `.lock` 未被任何进程持有」；Unix 再要求 pid 明确退出（EPERM / 其它错误视为无法确认 → 保留），**Windows 跳过 pid 判据**、只用时间 + 锁（`PidPolicy::Windows`，由 `cfg!` 选择）。
- **staging 所有权（文件在包目录之外）**：目录名带进程 pid + 随机后缀；所有权元数据写与 staging **同级的兄弟文件** `<staging 名>.owner.json`（pid + 创建时间）与 `<staging 名>.lock`，包目录里不写任何宿主文件（插件包自带 `owner.json` 时不会被覆盖，integrity 摘要安装后仍成立）。创建与解压都在跨进程锁内。启动清理只删「无事务引用 + 归属可读 + 所有者进程已不存在 + 超过 15 分钟 + 锁未被持有」的 staging，无法确认归属一律保留。pid 判据：Unix `kill(pid,0)` 返回 0 或 **EPERM（权限不足）按存活 / 无法确认处理**，只有 ESRCH 才算已退出；Windows 不实现 pid 查询，唯一判据是同级 `.lock` 未被任何进程持有（锁随进程退出由系统释放）。
- **清理范围只限当前事务登记的路径**：`cleanup_after_commit` 只删 `registered_paths`（记录里的 target / staging + `previous_state.version` 对应的旧版本目录，以及**本事务创建的** backup），**不再按插件 id 扫目录**；原来那个「只保留 keep、删掉其它全部目录」的 `prune_versions` 已移除；孤立的 `.old-*` 与未登记目录一律保留。
- **备份冲突在写事务记录之前拦下**：`begin_install` 先检查 `plugins/<id>/.old-<version>` 是否存在（**不论 target 在不在**），存在就直接返回「存在未确认的旧备份 .old-<version>，请先在插件面板移除或手工处理」——此时**不写事务记录、不写 .repair.json、不改 state、不动 target 与备份**，调用方只释放本次 staging，所以完好的插件不会被误禁用。`swap()` 里同样的检查只是兜底，遇到也直接报错、不改任何状态。
- **只删自己创建的备份**：记录里有 `backup_created` / `backup_identity`，只有在 `swap()` 把 target 改名为备份**成功之后**才认领（`advance` 落盘，落盘失败则回退这次改名）；清理（含非 committed 恢复分支）只有「backup_created 为真且当前备份身份等于 backup_identity」才删，否则保留并记日志。
- **已提交残留备份需要提交证据**：`commit()` 先把事务记录改写成 `stage=committed`（记录内含 target 身份 `new_id`），再按登记路径清理，最后才删记录；启动时只有「记录为 committed 且当前 target 身份 == new_id」才清理，身份不符 → 隔离。**没有任何事务记录的 `.old-*` 一律保留**（只记日志）；事务记录损坏 / 无法解析时本轮不删任何 staging 与 `.old-*`。
- **身份摘要流式化**：`tree_sha256` 逐文件固定缓冲读取，文件数 / 单文件 / 总字节与安装包上限一致；上限按**实际读到的字节**判定（文件在读取期间增长也会被发现，metadata 的旧长度不作数），超限即判身份未知，落到决策表第 8 行隔离，不把整目录读进内存。门禁锁中毒（`blocked` / `active`）时 `plugin_list` 把全部插件标不可用（`mark_unavailable`），与 scheme 一致，不用空集合冒充「没有禁用项」。
- **硬门槛一致性**：scheme 入口同时检查内存禁用集合（`PluginsState.blocked`）与事务集合，锁异常一律按禁用 / 空门禁处理；`plugin_set_enabled` 的修复标记、state 字段、内存禁用检查全部移进同一段文件锁 + 进程内锁。
- 主题同步：插件 iframe `load` 完成时宿主立即推送 `ready` 事件（内含初始 `{ theme: "light"|"dark", tokens }`，其中 `tokens` 为宿主 `:root` 上全部 `--*` CSS 变量的快照）；用户在宿主切换亮/暗色时，`MutationObserver` 监听 `html[data-theme]` 并实时向所有就绪插件推送 `theme-change` 事件；SDK（`sdk/devicedock-plugin.js`）默认在 `ready` 与 `theme-change` 时调用 `applyTheme()`，把 `data-theme` 与 `--*` 变量写到插件文档 `:root`。
- 语言跟随：宿主界面语言只有 `zh-CN` / `en`（配置页「语言」：跟随系统 / 中文 / English；跟随系统时 `navigator.language` 以 zh 开头为 `zh-CN`，否则 `en`）。插件 iframe 每次 `load` 后宿主紧跟 `ready` 推送状态事件 `app.locale`，载荷 `{ locale: "zh-CN" | "en" }`，按事件名合并最新态、保证送达、不占数据流配额；宿主切换语言会整页重载，插件随之重新 `load` 并收到新值。SDK 提供 `DeviceDockPlugin.getLocale()`（最近一次收到的值，尚未收到时为 `null`）与 `DeviceDockPlugin.onLocale(fn)`（订阅变化，订阅时已有值则立即回调一次，返回取消函数）。SDK 没有 `onLocale`（旧宿主）或尚未收到时，插件按 `navigator.language` 回退。插件自带文案，宿主不替插件翻译；示例见 `examples/plugin-hello/app.js`。
- 左栏与排序：已启用且支持当前系统的插件在左侧导航栏 `#rail-plugins`（「插件」分组）下生成标签，没有可用插件时整段隐藏；支持鼠标拖拽排序与聚焦后 `Alt+↑` / `Alt+↓` 键盘排序，顺序持久化在 `localStorage.pluginOrderV1`。
- 停用、卸载与应用更新准备：停用或卸载插件、或者应用进入更新冻结阶段（`prepare`）时，宿主立即销毁对应插件的 iframe、执行并**等待**全部 `teardown` 回调（BLE 扫描的所有权在启动前就登记，停用时等 `stopScan` 与扫描任务真实收尾；teardown 失败**不吞掉**，与串口关闭失败一起记进 `pendingReleases`）。`serial.claim` 的串口走统一异步关闭：作废在飞 `open()`、**等在飞 `claim.write` 结束**（写流还被锁着时不能 close）、取消并等待持锁 reader 与读循环、再 `close()`，关闭串行化避免并发重试。普通 `claim.close` 不置 `cancelled`，同一声明之后还能重新 `claim.open`；停用才永久作废。`claim.close` 一进入关闭就置 `closing`，等待在飞写入期间拒绝新 `claim.write`（`closing` 错误码），成功后才清 `closing`。释放失败保留占用声明与 busy 源，但**可重试**：每条释放记录只有一个在飞 Promise（管理面板 / 重开插件 / 更新路径并发触发复用同一个），重试开始即清 `failed` 且跳过已成功的 teardown；失败的资源留在宿主级 `pendingReleases` 列表里，即使插件被卸载，管理面板顶部也常显一条（插件 id、资源、原因、「重试释放」）。更新屏障 `app-update.js` 在 `blockers()` 之前先 `await pluginHost.retryAll()` 自动重试一次再判 busy；一直失败时 `plugin-host.release()` 抛错让更新冻结失败，不提前放行。未完成 / 失败的释放期间不会为同一插件创建新 iframe。
- 示例发布工作流固定 `runs-on: ubuntu-24.04`，`actions/checkout@v7.0.1` / `actions/setup-node@v7.1.0`（均为 node24 运行时的稳定版本）。
- GitHub 令牌：用于访问私有插件仓库或提高 GitHub API 限额，由 Rust 经 `keyring` 存入系统钥匙串（macOS 登录钥匙串 / Windows 凭据管理器，service `DeviceDock`、account `github-token`），不写 `localStorage`、不写应用数据目录文件；前端只能查 `plugin_token_status`（`{ set: bool }`）、设置新值或清除，永远无法读回令牌明文。
